# Feature Specification: 核心翻译能力——多翻译源接入（v0.0.3）

**Feature Branch**: `002-translation-providers`

**Created**: 2026-08-24

**Status**: Draft

**Input**: User description: "v0.0.3: 实现基本功能，其他 Vue+Vite 的前端项目接入之后，能快速实现 i18n 的支持，现在主要为验证阶段，能跑通流程就行。1. 需要支持配置 LLM 的 apikey 来实现翻译功能，能支持常见的 LLM 接口。2. 定义可以接口格式，用户可以提供一个实现了格式的接口，来完成翻译功能。3. 也可以使用一些免费的三方提供的翻译能力来实现翻译功能（比如谷歌翻译、微软翻译等）。并且这应该是没有配置前面两种情况下的默认行为。注意：测试的时候使用假数据或使用三方来免费测试，不要调用任何收费接口或 API 来测试。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 零配置默认翻译（免费三方翻译） (Priority: P1)

作为接入本插件的前端开发者，我在项目中接入插件后**不配置任何 API Key、不提供任何翻译实现**，启动开发服务器，页面中标记的待翻译文案会自动通过免费的三方翻译服务（如谷歌翻译免费接口）生成目标语言文案，并在切换语言时正确显示——即"开箱即用"的国际化。

**Why this priority**: 免费默认行为是本版本验证"其他 Vue+Vite 项目接入后能快速实现 i18n 支持"这一核心目标的最直接路径：接入方零成本（无需注册、无需付费）即可跑通完整流程，是三种翻译模式中使用门槛最低、验证价值最大的一个。

**Independent Test**: 在一个全新的 Vue+Vite 示例项目中只接入插件、不提供任何翻译配置，运行构建/开发流程后，翻译缓存文件中出现源语言与目标语言的文案对，页面运行时可切换显示译文。

**Acceptance Scenarios**:

1. **Given** 一个已接入插件的 Vue+Vite 项目且未配置 `translate` 与 `aiModelConfig`, **When** 开发构建执行到含待翻译文案的 `.vue` 文件, **Then** 插件自动选择免费三方翻译服务完成翻译，翻译结果写入翻译缓存
2. **Given** 免费翻译服务返回了译文, **When** 开发者在浏览器中切换语言, **Then** 页面文案显示对应目标语言译文
3. **Given** 免费翻译服务因网络原因请求失败, **When** 开发构建继续执行, **Then** 插件输出警告但不中断构建，源文案保持原样显示

---

### User Story 2 - 配置 LLM API Key 翻译 (Priority: P2)

作为对译文质量有更高要求的接入方开发者，我在插件配置中提供某个常见 LLM 服务商的 API Key（及可选的服务地址），插件改用该 LLM 完成文案翻译；配置了 LLM 时不再使用免费三方翻译。

**Why this priority**: LLM 翻译是本项目已有的差异化能力（v0.0.1 已支持智谱 GLM），本版本把它从"仅智谱"扩展为"常见 LLM 接口均可"，是插件核心能力的增强；优先级低于免费默认行为，因为它需要接入方自行注册并付费获取 Key。

**Independent Test**: 在插件配置中提供 LLM 的 API Key（OpenAI 兼容接口或智谱），运行开发构建，翻译缓存中的译文来自该 LLM；自动化测试中以假数据（stub 网络请求）验证请求格式与响应解析，不真实调用收费接口。

**Acceptance Scenarios**:

1. **Given** 插件配置了 OpenAI 兼容的 LLM（指定 API Key 与 baseUrl）, **When** 开发构建执行, **Then** 插件按该服务的聊天补全接口格式发起翻译请求并把译文写入翻译缓存
2. **Given** 插件配置了智谱 GLM 的 API Key, **When** 开发构建执行, **Then** 沿用智谱接口完成翻译（保持 v0.0.1 能力不回退）
3. **Given** 插件同时未配置 `translate` 但配置了 `aiModelConfig`, **When** 开发构建执行, **Then** 使用 LLM 而非免费三方翻译
4. **Given** 配置了无效的 API Key, **When** LLM 请求被服务端拒绝, **Then** 插件输出包含错误信息的警告，构建不中断

---

### User Story 3 - 自定义翻译接口 (Priority: P3)

作为有自建翻译服务或特殊翻译需求（术语表、内部机器翻译服务等）的接入方开发者，我按照插件定义并公开导出的翻译接口契约实现一个翻译函数，传入插件配置后，插件优先使用我的函数完成全部翻译。

**Why this priority**: 自定义接口是兜底的扩展能力，服务于少数有自建能力的接入方；它已经有事实上的契约存在（v0.0.1 的 `translate` 配置项），本版本的重点是把它固化为一等公民的公开契约并保证优先级最高，优先级因此低于前两种通用模式。

**Independent Test**: 实现一个符合契约的离线假翻译函数（如返回 `EN(原文)` 形式的字典），传入插件配置，运行开发构建后翻译缓存中的译文全部来自该函数。

**Acceptance Scenarios**:

1. **Given** 接入方提供了符合契约的 `translate` 函数, **When** 同时也配置了 LLM 与免费翻译可用, **Then** 插件优先且仅使用自定义函数完成翻译
2. **Given** 自定义函数对某批文案返回 `null`（表示本批无新增翻译）, **When** 构建结束, **Then** 插件不更新翻译缓存
3. **Given** 自定义函数抛出异常, **When** 构建继续, **Then** 插件捕获异常、输出警告且不中断构建

### Edge Cases

- 待翻译文案列表为空（当前模块无新增文案、或全部命中缓存）时，不得发起任何翻译请求
- 已存在于翻译缓存中的文案（源语言与全部目标语言均已翻译）不得重复翻译、重复计费或重复请求
- 文案中的插值占位符（如 `{name}`）翻译后必须原样保留，不得被翻译或破坏
- 免费三方服务对单次请求的文本数量/长度有限制时，必须分批请求并正确合并结果
- 内部语言枚举值（如日语 `jp`、阿拉伯语 `ara`、法语 `fra`）与三方服务语言代码（如 `ja`、`ar`、`fr`）不一致时必须正确映射
- 多目标语言（如同时翻译到英语与日语）时，每种目标语言都必须产出译文
- 生产构建（`isDev=false`）不注入开发期翻译代码，翻译缓存仍正常读取与保存

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 插件 MUST 按固定优先级自动选择翻译源：自定义翻译函数 > LLM（API Key）> 免费三方翻译；三者均以统一的内部翻译契约调用
- **FR-002**: 插件 MUST 支持通过 OpenAI 兼容的聊天补全接口使用 LLM 翻译（可配置服务地址 baseUrl 与 API Key），从而覆盖遵循该接口规范的服务商（OpenAI、DeepSeek、Moonshot、通义千问兼容模式、本地 Ollama 等）
- **FR-003**: 插件 MUST 保持既有智谱 GLM（glm-4）直连方式的可用性，配置智谱 API Key 时不要求额外改动
- **FR-004**: 未配置自定义函数与 LLM 时，插件 MUST 默认使用无需 API Key 的免费三方翻译服务（谷歌翻译免费接口）完成翻译，接入方零配置即可跑通流程
- **FR-005**: 插件 MUST 公开导出自定义翻译接口契约（TypeScript 类型），接入方可据此实现自己的翻译函数，且该契约在三种翻译源间通用
- **FR-006**: 翻译过程 MUST 保持插值占位符（`{name}` 形式）在译文中原样保留
- **FR-007**: 任何翻译源发生错误（网络失败、鉴权失败、响应格式异常、实现方抛错）时，插件 MUST 捕获并输出含错误信息的警告，且 MUST NOT 中断构建/开发流程
- **FR-008**: 插件 MUST 复用既有翻译缓存：命中缓存（源语言与全部目标语言均已存在）的文案不重复发起翻译请求
- **FR-009**: 内部语言枚举到三方服务语言代码 MUST 存在显式映射（如 `jp→ja`、`ara→ar`、`fra→fr`），映射缺失时跳过该目标语言并警告
- **FR-010**: 免费三方翻译 MUST 支持对长列表分批请求并合并结果，单批失败只影响该批（警告并跳过），不影响其他批次
- **FR-011**: 全部自动化测试 MUST 离线运行（以假数据/stub 网络请求验证请求构造、响应解析与错误路径），MUST NOT 调用任何收费 API；对免费三方可做一次性人工验证且不得进入自动化测试
- **FR-012**: 三种翻译模式 MUST 均可通过统一的 Use Case 流程验证：读取缓存 → 提取文案 → 调用翻译源 → 合并缓存 → 保存缓存 → 开发期注入

### Key Entities

- **翻译源（Translate Provider）**: 完成文案翻译的能力单元，分三类——自定义函数、LLM 服务、免费三方服务；对外统一为"输入待翻译文案列表+源语言+目标语言列表+缓存，输出新增译文映射或空"
- **翻译接口契约（Translate Contract）**: 插件公开导出的函数类型约定，是三种翻译源的统一调用格式，也是接入方实现自定义翻译的唯一依赖
- **翻译缓存（Translate Cache）**: 以源文案哈希为键、语言到译文的映射为值的数据文件，跨构建持久化，用于避免重复翻译
- **LLM 配置（LLM Config）**: 接入方提供的 LLM 服务选择、API Key 与可选服务地址
- **语言（Language）**: 插件内部语言枚举及其到各三方服务语言代码的映射

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一个新的 Vue+Vite 项目按 README 接入步骤安装并配置插件（不提供任何翻译配置），首次开发构建即可自动生成目标语言文案并在页面切换语言时正确显示，全程无需注册任何三方账号
- **SC-002**: 接入方仅提供 API Key 与服务地址即可切换到任一 OpenAI 兼容 LLM 完成翻译，无需改动插件代码
- **SC-003**: 接入方提供符合公开契约的自定义翻译函数后，该函数被优先且独占地用于全部翻译
- **SC-004**: 三种翻译模式各有自动化测试覆盖（含正常路径与错误路径），全部测试离线运行且通过（`pnpm test:all` 成功，CI 校验通过）
- **SC-005**: 全部既有测试（v0.0.2 建立的单元/集成/Use Case/e2e）保持通过，不因本版本改动回退

## Assumptions

- 免费三方翻译采用谷歌翻译的免费网页接口（`translate.googleapis.com/translate_a/single?client=gtx`）：无需 API Key、不产生费用；该接口属非官方约定，验证阶段可接受，后续版本可替换为自托管或更稳定方案（如 LibreTranslate、微软 Edge 免费接口）
- "常见 LLM 接口"以 OpenAI Chat Completions 兼容格式为标准（业界事实标准，DeepSeek/Kimi/通义/智谱/Ollama 等均提供兼容端点）；智谱 GLM 直连方式作为历史能力保留
- 免费接口存在速率与批量限制，本阶段采用简单分批+失败警告策略，不实现复杂的退避重试、并发调度或配额管理
- 译文质量控制（术语表、上下文提示词调优）不在本版本范围内；本版本目标是"跑通流程"的验证阶段
- 运行时（浏览器端）翻译加载、语言切换、`{name}` 插值等能力沿用 v0.0.1 既有实现，不在本版本重做
- 自动化测试一律使用假数据与 stub 网络；对免费三方接口的一次性真实验证由开发者手动执行并记录，不纳入 CI
